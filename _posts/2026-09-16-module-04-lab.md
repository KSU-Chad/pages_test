## Part 1 — Broadcasting a Static Transform Chain

**Goal:** build a small transform tree by hand and watch it in RViz2.

1. Open a terminal and broadcast a transform from `world` to `robot_1`, translated (2, 1, 0) and rotated 45 degrees (0.785 rad) in yaw:

   ```bash
   ros2 run tf2_ros static_transform_publisher 2 1 0 0.785 0 0 world robot_1
   ```

2. In a second terminal, broadcast a "sidecar" frame, `robot_2`, sitting 1m over from `robot_1`:

   ```bash
   ros2 run tf2_ros static_transform_publisher 1 0 0 0 0 0 robot_1 robot_2
   ```

3. In a third terminal, launch RViz2:

   ```bash
   ros2 run rviz2 rviz2
   ```

4. Click **Add** (bottom-left) and select **TF**.

5. In the top-left, set **Fixed Frame** to `world`. (It defaults to `map`, which doesn't exist yet — nothing will appear until you change this.)

6. You should now see both frames, connected by a line. In the TF display's settings (left panel), enable frame name labels if they aren't already on.

7. **Try it yourself:** stop the first `static_transform_publisher`, and restart it with a bigger rotation, 90 degrees (1.57 rad) instead of 45:

   ```bash
   ros2 run tf2_ros static_transform_publisher 2 1 0 1.57 0 0 world robot_1
   ```

   Watch both `robot_1` and `robot_2` rotate. `robot_2` moves because it's defined relative to `robot_1`, not to `world`.

8. **Explore on your own:** change the Fixed Frame (top-left) to `robot_1` instead of `world`, and see how the view changes. Try adding a third frame of your own, defined relative to whichever frame you like.

9. When you're done, **stop both `static_transform_publisher` processes and close RViz2** before moving to Part 2 — leftover static transforms will interfere with what comes next.

**Check your understanding:** RViz draws the transform arrow from child to parent, the opposite direction from how you typed the command. Why might that be a confusing detail to forget about later?

## Part 2 — Bringing Up a Moving Robot (a Manipulator Arm)

**Goal:** use a real multi-joint manipulator arm's URDF to see `robot_state_publisher` and `joint_state_publisher_gui` broadcast a moving robot's transforms automatically.

**Why an arm, in a mobile robotics course?** Everything you're about to do — frames, transforms, forward kinematics — applies just as much to a Mecanum-wheeled MentorPi as it does to an industrial arm. An arm is actually the *clearer* first example: each joint's motion is a single, visible rotation, so it's easy to see forward kinematics happening (each joint's transform, chained together, tells you exactly where the gripper ends up). Once you've seen that chain on an arm, the same idea applies to your MentorPi's odometry later this semester — it's computing the robot's pose from wheel motion the same way this arm computes its gripper's pose from joint motion, just with different math underneath.

1. Confirm you have the required packages:

   ```bash
   sudo apt install ros-jazzy-xacro ros-jazzy-joint-state-publisher-gui
   ```

2. Clone Josh Newans' example URDF repo into your workspace's `src/`:

   ```bash
   cd ~/ros2_ws/src
   git clone https://github.com/joshnewans/urdf_example.git
   ```

3. Build it and source your workspace:

   ```bash
   cd ~/ros2_ws
   colcon build --packages-select urdf_example
   source install/setup.bash
   ```

4. Launch the `robot_state_publisher`:

   ```bash
   ros2 launch urdf_example rsp.launch.py
   ```

   Under the hood, this launch file is running something equivalent to:

   ```bash
   ros2 run robot_state_publisher robot_state_publisher --ros-args -p robot_description:="$(xacro path/to/file.urdf.xacro)"
   ```

5. In a second terminal, start the joint state GUI:

   ```bash
   ros2 run joint_state_publisher_gui joint_state_publisher_gui
   ```

6. In a third terminal, open RViz2:

   ```bash
   rviz2
   ```

   Set **Fixed Frame** to `world`, add a **RobotModel** display with topic `/robot_description` (set alpha to 0.8), and add a **TF** display with names enabled.

7. Move the sliders in `joint_state_publisher_gui` and watch the arm's joints move in RViz2 — notice how moving `arm_joint` (revolute) swings `arm_link` through a limited range, while `slider_joint` (prismatic) slides `slider_link` back and forth in a straight line, exactly as covered in lecture.

**Check your understanding:** if you closed `joint_state_publisher_gui`, would the robot's pose in RViz disappear, or freeze in place? Try it and see if you predicted correctly.

**Check your understanding (the bigger point):** this arm has, say, five or six joints, each contributing one rotation to the final gripper position. A MentorPi has four wheels instead. What do you think plays the role of "joint angle" in figuring out how far the *MentorPi* has moved, instead of a joint's rotation angle?

## Part 3 — Viewing the Whole Tree with `view_frames`

**Goal:** generate a diagram of your transform tree and compare its arrow direction to what you saw in RViz.

1. With your Part 2 setup still running, open a new terminal and run:

   ```bash
   ros2 run tf2_tools view_frames.py
   ```

2. Wait a few seconds — it listens to the transform topics, then generates `frames.pdf` (and `frames.gv`) in your current directory.

3. Open `frames.pdf`. Note the arrow direction: parent to child, matching how you actually typed the frames, the opposite of RViz's child-to-parent convention.

4. Identify which frame is the root of your tree, and which frames are its direct children.

**Check your understanding:** if a frame's connection in `view_frames` looked "stale" (a very old timestamp), what would that tell you about the node broadcasting it?

## Troubleshooting Tips

- **Nothing shows up in RViz:** check the Fixed Frame setting first; it defaults to `map`, which won't exist in this lab
- **`robot_state_publisher` complains about `robot_description`:** it wants the full URDF contents, not a file path; this is exactly why the provided `rsp.launch.py` exists, so use it rather than typing the raw command by hand
- **`ros2 launch urdf_example rsp.launch.py` fails with "package not found":** confirm you built and sourced *after* cloning — a clone alone doesn't make ROS 2 aware of the package
- **Sliders in `joint_state_publisher_gui` don't do anything:** confirm `robot_state_publisher` is actually running first, and that RViz's RobotModel display is pointed at `/robot_description`
- **`view_frames.py` produces an empty or near-empty tree:** confirm your Part 2 nodes are still running when you run it; it only listens for a few seconds and needs live transforms to capture
- **Static transforms from Part 1 are still showing up in Part 2:** make sure you actually stopped those processes; they don't stop just because you closed the terminal window if they were run in the background
