### 4.6 — Teach the robot Pi its USB devices *(robot Pi only)*

The motor board, lidar and camera all show up as USB devices with names like `/dev/ttyUSB0`. Those numbers change between boots. A **udev rule** gives each device a permanent name. The launch file uses `/dev/rrc` (motor board) and `/dev/ldlidar` (lidar).

**Motor board.** Create the rule file:

```bash
sudo nano /etc/udev/rules.d/99-rrc.rules
```

Paste this one line, then save (Ctrl+O, Enter, Ctrl+X):

```
KERNEL=="ttyACM*", SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="55d4", SYMLINK+="rrc", MODE="0666", GROUP="dialout", ENV{ID_MM_PORT_IGNORE}="1"
```

**Lidar.** Find its USB IDs. Unplug everything except the lidar adapter, then run:

```bash
lsusb
```

The lidar adapter is the new line. The two codes after `ID` are `<vendor>:<product>`. Example: `ID 10c4:ea60` means vendor `10c4`, product `ea60`.

**Confirm with the device itself (the lidar should appear as `ttyUSB0`):**

```bash
udevadm info -a -n /dev/ttyUSB0 | grep -E "idVendor|idProduct" | head -2
```

> **Write down:** vendor `________` product `________`

Create the lidar rule file:

```bash
sudo nano /etc/udev/rules.d/99-ldlidar.rules
```

Paste this line, replacing `VVVV` and `PPPP` with **your** vendor and product codes:

```
SUBSYSTEM=="tty", ATTRS{idVendor}=="VVVV", ATTRS{idProduct}=="PPPP", SYMLINK+="ldlidar", MODE="0666"
```

> **Instructor:** after you run `lsusb` on a real MentorPi, replace `VVVV` and `PPPP` here with the real codes so students can paste it directly. (Many LD19 kits use a CP210x adapter, `10c4:ea60`. Confirm on your units.)

**Depth camera.** The camera package ships its own rule file. Find it and copy it:

```bash
find ~/ros2_ws/src/ascamera -name "angstrong-camera.rules"
```

```bash
sudo cp <path-printed-above> /etc/udev/rules.d/
```

**Load all the new rules, then unplug and replug the lidar, camera and motor board:**

```bash
sudo udevadm control --reload-rules && sudo udevadm trigger
```

**Check the names exist:**

```bash
ls -l /dev/rrc /dev/ldlidar
```

☐ Both names print and point at a `ttyACM` or `ttyUSB` device. If one is missing, re-check the vendor/product codes for that device.

## Part 5 — Netplan: Move to the Robot Network

**Goal:** the Pi joins `RAS-Robots` at its fixed address every time it boots.

**Netplan** is Ubuntu's network config system. You write a YAML file describing what you want, and Netplan turns it into settings for NetworkManager.

> **Do this part at the Pi's own keyboard and monitor, not over SSH.** If you make a typo, you lose the network, and the monitor is how you fix it.

*Do this on both Pis, one at a time.*

### 5.1 — Look before you change

**What are the network cards called? (The Wi-Fi one should be `wlan0`.)**

```bash
ip -br addr
```

**What Netplan files already exist?**

```bash
ls /etc/netplan
```

Netplan reads files in alphabetical order, and later files win. Ours is named `90-robot-network.yaml`, so it goes last.

### 5.2 — Write the file

**Set your numbers (same terminal for the next two commands; change `01` to yours).**

On the **robot Pi**:

```bash
NN=01
IP_END=1${NN}
WIFI_PW='password-from-your-instructor'
```

On the **desk Pi**, the address starts with a `2` instead:

```bash
NN=01
IP_END=2${NN}
WIFI_PW='password-from-your-instructor'
```

**Create the Netplan file:**

```bash
sudo tee /etc/netplan/90-robot-network.yaml > /dev/null <<EOF
network:
  version: 2
  renderer: NetworkManager
  wifis:
    wlan0:
      dhcp4: false
      addresses: [192.168.0.${IP_END}/24]
      access-points:
        "RAS-Robots":
          password: "${WIFI_PW}"
EOF
```

**Look at what you wrote. Is the address right? (Station 03 should show `192.168.0.103/24` on the robot Pi and `192.168.0.203/24` on the desk Pi.)**

```bash
sudo cat /etc/netplan/90-robot-network.yaml
```

Notice there's **no gateway and no DNS**. The robot network has no internet, so there's nowhere to send that traffic anyway.

**Lock the file down (it has a Wi-Fi password in it, and Netplan complains if other users can read it):**

```bash
sudo chmod 600 /etc/netplan/90-robot-network.yaml
```

**Check the YAML for mistakes (no output means it's good):**

```bash

```

**Apply it:**


## Part 7 — ROS 2 Network Settings and the Clock

**Goal:** both Pis speak the same ROS 2 dialect, agree on what time it is, and nobody else's robot hears you.

Four settings matter:

| Setting | What it does |
|---|---|
| `ROS_DOMAIN_ID` | Your private channel. Same number on your robot Pi and desk Pi, so you only hear *your* robot |
| `RMW_IMPLEMENTATION` | Which DDS library carries the messages. Both sides must match. We use CycloneDDS |
| `ROS_AUTOMATIC_DISCOVERY_RANGE` | How far to look for other ROS nodes. `SUBNET` means this network only |
| `CYCLONEDDS_URI` | Points to a config file that pins CycloneDDS to the Wi-Fi card |

Both Pis use the **same files**. Do 7.1 on the robot over SSH, then do it again on the desk Pi at its own keyboard.

### 7.1 — The ROS settings *(both Pis)*

**Set your station number again (a new terminal forgets it):**

```bash
NN=01
```

**Make the config folder:**

```bash
sudo mkdir -p /etc/ros
```

**Write the CycloneDDS config (this pins it to the Wi-Fi card):**

```bash
sudo tee /etc/ros/cyclonedds.xml > /dev/null <<'EOF'
<CycloneDDS xmlns="https://cdds.io/config">
  <Domain Id="any">
    <General>
      <Interfaces>
        <NetworkInterface name="wlan0"/>
      </Interfaces>
      <AllowMulticast>spdp</AllowMulticast>
    </General>
  </Domain>
</CycloneDDS>
EOF
```

**Write the settings file (the `10#` keeps `08` from being read as octal):**

```bash
sudo tee /etc/robot.env > /dev/null <<EOF
ROS_DOMAIN_ID=$((10#${NN}))
RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET
CYCLONEDDS_URI=file:///etc/ros/cyclonedds.xml
EOF
```

**Check it (station 03 should show `ROS_DOMAIN_ID=3`):**

```bash
cat /etc/robot.env
```

**Make every new terminal load these settings and ROS 2:**

```bash
echo 'set -a; source /etc/robot.env; set +a' >> ~/.bashrc
```

```bash
echo 'source /opt/ros/jazzy/setup.bash' >> ~/.bashrc
```

```bash
echo 'source ~/ros2_ws/install/setup.bash' >> ~/.bashrc
```

**Load them into this terminal now:**

```bash
source ~/.bashrc
```

**Confirm:**

```bash
printenv | grep -E 'ROS|RMW|CYCLONE'
```

### 7.2 — Whose clock is it?

ROS stamps every message with a time. Later, ROS uses those stamps to match a lidar scan to where the robot was at that moment. If your two Pis disagree about the time, RViz throws data away.

Neither Pi has internet now, and the Pi has no battery-backed clock by default. So we pick **one clock** and make the other follow it. The **desk Pi is the time server**, and the robot Pi follows.

> The time doesn't have to be *correct*. It only has to be the **same** on both Pis.

**On the desk Pi:**

```bash
sudo tee /etc/chrony/conf.d/robot-time.conf > /dev/null <<'EOF'
allow 192.168.0.0/24
local stratum 10
EOF
```

```bash
sudo systemctl restart chrony
```

**On the robot Pi (over SSH; set `NN` first if this is a new terminal):**

```bash
sudo tee /etc/chrony/conf.d/robot-time.conf > /dev/null <<EOF
server 192.168.0.2${NN} iburst prefer
makestep 1 -1
EOF
```

```bash
sudo systemctl restart chrony
```

**Wait a minute, then check it on the robot Pi:**

```bash
chronyc sources
```

You want a line for `192.168.0.2NN` that starts with `^*` or `^+`. That means the robot Pi is following the desk Pi.

**Compare the two clocks. Run this on the desk Pi, then on the robot Pi. The numbers should be within a second or so:**

```bash
date +%s
```

**Check your understanding:** your robot Pi gets its time from the desk Pi, and the desk Pi gets its time from nowhere. Why does that work for ROS?

**Check your understanding:** your robot is `robot08`, domain ID `8`. Your neighbor's is `robot09`, domain ID `9`. You're on the same Wi-Fi and the same subnet. Why don't you see each other's topics?

## Part 9 — Autostart: A Robot That Wakes Up Ready

**Goal:** the robot starts its own bringup at power-on. No SSH, no typing.

**systemd** is the part of Linux that starts things at boot. A **service file** tells it what to run, as who, and when.

> **Safety first.** Put the robot on a stand or give it clear floor before you test this. A robot that starts itself might also move itself.

*This part is for the robot Pi only.*

**One thing the launch file must do first: set `MACHINE_TYPE`.** Hiwonder's robot description and its odometry node both read an environment variable named `MACHINE_TYPE`. A service started by systemd doesn't load your terminal settings, so without this the robot fails at boot. Put these two lines at the very top of `robot.launch.py`, the same way `launch_sim.launch.py` does it:

```python
import os
os.environ.setdefault('MACHINE_TYPE', 'MentorPi_Mecanum')
```

`setdefault` only sets the value if nothing else already did, so it's safe to leave in.


**On the robot Pi (SSH). Write the service file** (`$USER` fills in your username, and `robot.launch.py` is the launch file your instructor named for the real robot):

```bash
sudo tee /etc/systemd/system/robot-bringup.service > /dev/null <<EOF
[Unit]
Description=Robot bringup (ROS 2)
After=network-online.target
Wants=network-online.target

[Service]
User=${USER}
EnvironmentFile=/etc/robot.env
Environment=PYTHONUNBUFFERED=1
ExecStart=/bin/bash -c 'source /opt/ros/jazzy/setup.bash && source /home/${USER}/ros2_ws/install/setup.bash && exec ros2 launch mentorpi_bringup robot.launch.py'
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF
```

What each section does:
- `After=network-online.target`: wait for Wi-Fi first
- `User=` and `EnvironmentFile=`: run as you, with your `/etc/robot.env` settings
- `ExecStart=`: the one command that starts the robot
- `Restart=on-failure`: if it crashes, try again in 5 seconds
- `WantedBy=multi-user.target`: start at boot

**Tell systemd about the new file:**

```bash
sudo systemctl daemon-reload
```

**Start it now and at every boot:**

```bash
sudo systemctl enable --now robot-bringup.service
```

**Is it running? (look for `active (running)`)**

```bash
systemctl status robot-bringup.service
```

**Watch its output live (`Ctrl+C` to stop watching; the robot keeps running):**

```bash
journalctl -u robot-bringup -f
```

**The real test: reboot.**

```bash
sudo reboot
```

Wait about a minute. Then, on your desk Pi, without touching the robot:

```bash
ros2 topic list
```

You should see the robot's topics. Find the **lidar** and **camera** topics in the list. You'll use them in Module 12.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Pi 5 shows no picture | Monitor wasn't plugged in at boot | Plug in the monitor first (use the HDMI port next to the USB-C power), then power on |
| `ping ubuntu.com` fails on guest Wi-Fi | Portal not accepted, or it timed out | Open Firefox, accept the terms again |
| `ROS_APT_SOURCE_VERSION` is blank | GitHub limits requests per address, and the whole lab shares one | Wait a few minutes, or ask your instructor for the version number and set it by hand |
| `apt` can't find `ros-jazzy-...` | Package source missing | Redo 4.3, then `sudo apt update` |
| `sudo rosdep init` says file exists | Already initialized | Fine. Go on to `rosdep update` |
| `colcon build` fails on the robot Pi | Missing dependency | Re-run the `rosdep install` command. Read the first error, not the last |
| `ros2 pkg prefix mentorpi_description` fails on the desk Pi | Package not built, or `setup.bash` not loaded | Re-run the desk Pi build in 4.5, then `source ~/ros2_ws/install/setup.bash` |
| `netplan generate` complains about permissions | File is readable by everyone | `sudo chmod 600 /etc/netplan/90-robot-network.yaml` |
| `netplan generate` complains about syntax | YAML indentation | Spaces only, no tabs. Compare to Part 5 line by line |
| Pi didn't join `RAS-Robots` | Guest Wi-Fi won instead | Turn off its autoconnect (5.3), then `sudo nmcli connection up netplan-wlan0-RAS-Robots` |
| Pi lost the network completely | Typo in the Netplan file | Plug in the monitor, fix `/etc/netplan/90-robot-network.yaml`, run `sudo netplan apply` |
| Desk Pi can't ping the robot | Wrong address on one Pi, or the robot Pi is off | `ip -br addr show wlan0` on each Pi. Robot is `192.168.0.1NN`, desk is `192.168.0.2NN` |
| `ssh` says `Connection refused` | SSH server not running | On the robot Pi: `sudo systemctl enable --now ssh` |
| `ssh` says `Host key verification failed` | You re-flashed the card and the fingerprint changed | `ssh-keygen -R 192.168.0.1NN`, then try again |
| `.local` name doesn't work | The router blocks name discovery | Use the IP address |
| `chronyc sources` doesn't list the desk Pi | Desk Pi's `chrony` config missing, or chrony not restarted | On the desk Pi: `cat /etc/chrony/conf.d/robot-time.conf`, then `sudo systemctl restart chrony`. Do the same on the robot Pi |
| `ros2 topic list` is empty on the desk Pi | Wrong domain, or the settings aren't loaded in this terminal | `source ~/.bashrc`. Compare `printenv \| grep ROS` on both Pis |
| Topics show up on the robot but not the desk Pi | DDS bound to the wrong network card, or Wi-Fi is blocking multicast | Check `cyclonedds.xml` says `wlan0` on both. Then try the unicast fallback below |
| `ROS_DOMAIN_ID ... is not an integer` | Leading zero (like `08`) | Use `$((10#${NN}))` as in Part 7 |
| Service says `failed` | Wrong launch file name, or workspace not built | `journalctl -u robot-bringup -n 50`. Read it from the **bottom** |
| Service runs but no topics | Started before the Wi-Fi was ready | `sudo systemctl restart robot-bringup.service`. Check `After=network-online.target` |
| Need the desktop for troubleshooting | Robot is set to headless | `sudo systemctl start gdm3` |

### Fallback: unicast discovery

If Parts 1 to 8 are right but the Pis can't see each other's topics, the Wi-Fi may be blocking multicast. Each Pi can be told the other's address directly. The ping must work first.

**On the robot Pi** (set `NN` first):

```bash
sudo tee /etc/ros/cyclonedds.xml > /dev/null <<EOF
<CycloneDDS xmlns="https://cdds.io/config">
  <Domain Id="any">
    <General>
      <Interfaces>
        <NetworkInterface name="wlan0"/>
      </Interfaces>
      <AllowMulticast>false</AllowMulticast>
    </General>
    <Discovery>
      <Peers>
        <Peer address="192.168.0.2${NN}"/>
      </Peers>
    </Discovery>
  </Domain>
</CycloneDDS>
EOF
```

**On the desk Pi** (set `NN` first). The peer is the robot this time:

```bash
sudo tee /etc/ros/cyclonedds.xml > /dev/null <<EOF
<CycloneDDS xmlns="https://cdds.io/config">
  <Domain Id="any">
    <General>
      <Interfaces>
        <NetworkInterface name="wlan0"/>
      </Interfaces>
      <AllowMulticast>false</AllowMulticast>
    </General>
    <Discovery>
      <Peers>
        <Peer address="192.168.0.1${NN}"/>
      </Peers>
    </Discovery>
  </Domain>
</CycloneDDS>
EOF
```

Restart anything that was running (`sudo systemctl restart robot-bringup.service` on the robot, new terminals on the desk Pi) and test again. With this fallback you only see your own robot, so the "neighbor's robot" step in Module 12 won't work. Skip it.
