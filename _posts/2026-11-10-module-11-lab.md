# Lab 11 — Bringing Up a Robot: Raspberry Pi, Network, and ROS 2


## Part 1 — Flash the SD Card

**Goal:** Ubuntu Desktop 24.04 on the card.

On your laptop, open **Raspberry Pi Imager** and choose:

1. **Device:** Raspberry Pi 5
2. **Operating System:** Other general-purpose OS → Ubuntu → **Ubuntu Desktop 24.04 LTS (64-bit)**
3. **Storage:** your microSD card
4. Write the card, then put it in the Pi.

Raspberry Pi Imager offers customization for Raspberry Pi OS but not for Ubuntu. That's why we connect a monitor and keyboard to configure the Pi.

**Plug in the monitor, keyboard, and mouse first, then power.** The Pi only checks for a monitor at boot, and it turns off the desktop if it doesn't find one.

## Part 2 — First Boot and the Setup Wizard

**Goal:** a Pi with your name, your computer name, and your account.

The first boot takes a few minutes. Work through the wizard. When it asks about **your name, your computer's name, and username**, here is what each one actually does:

| Wizard field | What it's for | Why it matters |
|---|---|---|
| **Your name** | The friendly name on the login screen ("Welcome, Alex") | Nothing technical depends on it. Use whatever you like |
| **Your computer's name** | The **hostname**: how the robot shows up on the network and in your terminal prompt (`user@robot03`) | It has to be **unique**, because it's how you tell robots apart. Use `robotNN`, lowercase, no spaces or underscores |
| **Username** | The login **account**. It sets your home folder (`/home/username`) and is what you type in `ssh username@...` | The autostart service runs *as this user*, and it's a pain to change later. Use the one your instructor gave you |
| **Password** | Needed for `sudo` and for SSH | You'll type it a lot. Don't forget it |

Use **Central Time** and the US keyboard layout.

Skip the WiFi configuration for now.

When you see the desktop, open the terminal.

**Check the names stuck**

```bash
hostnamectl
```

Look at **Static hostname**. If it isn't `robotNN`, fix it (replace `robot03` with yours):

```bash
sudo hostnamectl set-hostname robot03
```

**Check your understanding:** two robots both named `ubuntu` are on the same network. What goes wrong?

## Part 5 — Netplan: Move to the Robot Network

**Goal:** both computers join `Rogue_Network` at their own fixed address.

The robot Pi uses **Netplan**, Ubuntu's network config system. You write a YAML file describing what you want, and Netplan turns it into settings for NetworkManager. Your laptop uses one `nmcli` command instead, so it can still join other networks later.

### 5.1 — Robot Pi: look before you change

> **Do this part at the Pi's own keyboard and monitor, not over SSH.** If you make a typo, you lose the network, and the monitor is how you fix it.

**What are the network cards called? (The Wi-Fi one should be `wlan0`.)**

```bash
ip -br addr
```

**What Netplan files already exist?**

```bash
ls /etc/netplan
```

Netplan reads files in alphabetical order, and later files win. Ours is named `90-robot-network.yaml`, so it goes last.

### 5.2 — Robot Pi: write the file

**Type these two lines in the terminal, pressing Enter after each.** Change `01` to your robot number and put in the real Wi-Fi password. They don't go in any file. The next command reads them and fills in the file for you. **Stay in this same terminal until you've run that command.**

```bash
NN=01
WIFI_PW='password-from-your-instructor'
```

**Create the Netplan file:**

```bash
sudo tee /etc/netplan/90-robot-network.yaml > /dev/null <<EOF
network:
  version: 2
  renderer: NetworkManager
  wifis:
    wlan0:
      dhcp4: false
      addresses: [192.168.0.1${NN}/24]
      access-points:
        "Rogue_Network":
          password: "${WIFI_PW}"
EOF
```

**Look at what you wrote. Is the address right? (Robot 03 should show `192.168.0.103/24`.)**

```bash
sudo cat /etc/netplan/90-robot-network.yaml
```

Notice there's **no gateway and no DNS**. The robot network has no internet, so there's nowhere to send that traffic anyway.

**Lock the file down (it has a Wi-Fi password in it, and Netplan complains if other users can read it):**

```bash
sudo chmod 600 /etc/netplan/90-robot-network.yaml
```

### 5.3 — Robot Pi: apply it

**Check the YAML for mistakes (no output means it's good):**

```bash
sudo netplan generate
```

**Apply it:**

```bash
sudo netplan apply
```

**Tell the Pi to stop auto-joining the guest Wi-Fi, so it doesn't wander back. First find its name:**

```bash
nmcli connection show
```

**Then turn off its autoconnect (put the guest connection's name in the quotes):**

```bash
sudo nmcli connection modify "KSU-Guest" connection.autoconnect no
```

**If the Pi is still on the guest network, switch it by hand:**

```bash
sudo nmcli connection up netplan-wlan0-Rogue_Network
```

**Do you have the right address?**

```bash
ip -br addr show wlan0
```

**Can you reach the router?**

```bash
ping -c 3 192.168.0.50
```

☐ The Pi has the right address and can ping the router.

> **No internet on the Pi now, and that's correct.** If you ever need updates again, see the box at the end of Part 11.

### 5.4 — Laptop: join the robot network

*Same as in step 5.2, but now on the laptop*

**Type these two lines in the terminal, pressing Enter after each.** Change `01` to your robot number and put in the real Wi-Fi password. They don't go in any file. The next command reads them and fills in the file for you. **Stay in this same terminal until you've run that command.**

## Part 7 — ROS 2 Network Settings and the Clock

**Goal:** both computers speak the same ROS 2 dialect, agree on what time it is, and nobody else's robot hears you.

Four settings matter:

| Setting | What it does |
|---|---|
| `ROS_DOMAIN_ID` | Your private channel. Same number on the robot and laptop, so you only hear *your* robot |
| `RMW_IMPLEMENTATION` | Which DDS library carries the messages. Both sides must match. We use CycloneDDS |
| `ROS_AUTOMATIC_DISCOVERY_RANGE` | How far to look for other ROS nodes. `SUBNET` means this network only |
| `CYCLONEDDS_URI` | Points to a config file that pins CycloneDDS to the right network card |

### 7.1 — On the robot Pi (over SSH)

**Set your number again (a new terminal forgets it):**

```bash
NN=01
```

**Make the config folder:**

```bash
sudo mkdir -p /etc/ros
```

**Write the CycloneDDS config (this pins it to the Wi-Fi card):**

```bash
sudo tee /etc/ros/cyclonedds.xml > /dev/null <<'EOF'
<CycloneDDS xmlns="https://cdds.io/config">
  <Domain Id="any">
    <General>
      <Interfaces>
        <NetworkInterface name="wlan0"/>
      </Interfaces>
      <AllowMulticast>spdp</AllowMulticast>
    </General>
  </Domain>
</CycloneDDS>
EOF
```

**Write the settings file (the `10#` keeps `08` from being read as octal):**

```bash
sudo tee /etc/robot.env > /dev/null <<EOF
ROS_DOMAIN_ID=$((10#${NN}))
RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET
CYCLONEDDS_URI=file:///etc/ros/cyclonedds.xml
EOF
```

**Check it (Robot 03 should show `ROS_DOMAIN_ID=3`):**

```bash
cat /etc/robot.env
```

**Make every new terminal load these settings and your workspace:**

```bash
echo 'set -a; source /etc/robot.env; set +a' >> ~/.bashrc
```

```bash
echo 'source ~/ros2_ws/install/setup.bash' >> ~/.bashrc
```

**Load them into this terminal now:**

```bash
source ~/.bashrc
```

**Confirm:**

```bash
printenv | grep -E 'ROS|RMW|CYCLONE'
```

### 7.2 — On your laptop

Your laptop is used for other things too, so we don't change its `.bashrc`. We put the settings in one file and load it **in each terminal you use for the robot**.

**Type this line in the terminal. Change `01` to your robot number. The next commands read it:**

**Write the CycloneDDS config (this pins it to your laptop's robot-network address, since the card name varies):**

**Write the settings file:**

**Load it (do this in every new laptop terminal you use for the robot):**


**Confirm:**


### 7.3 — Whose clock is it?

ROS stamps every message with a time. Later, ROS uses those stamps to match a lidar scan to where the robot was at that moment. If your two computers disagree about the time, RViz throws data away.

The robot Pi has no battery-backed clock, and it has no internet now. So we pick **one clock** and make the Pi follow it. **Your laptop is the time server**, and the robot Pi follows.

> The time doesn't have to be *correct*. It only has to be the **same** on both.

**On your laptop:**

```bash
sudo tee /etc/chrony/conf.d/robot-time.conf > /dev/null <<'EOF'
allow 192.168.0.0/24
local stratum 10
EOF
```

```bash
sudo systemctl restart chrony
```

**On the robot Pi (over SSH; set `NN` first if this is a new terminal):**

```bash
sudo tee /etc/chrony/conf.d/robot-time.conf > /dev/null <<EOF
server 192.168.0.2${NN} iburst prefer
makestep 1 -1
EOF
```

```bash
sudo systemctl restart chrony
```

**Wait a minute, then check it on the robot Pi:**

```bash
chronyc sources
```

You want a line for `192.168.0.2NN` that starts with `^*` or `^+`. That means the Pi is following your laptop.

**Compare the two clocks. Run this on your laptop, then on the robot Pi. The numbers should be within a second or so:**

```bash
date +%s
```

**Check your understanding:** your Pi gets its time from your laptop. Why does it not matter if your laptop's clock is a few minutes off real time?

**Check your understanding:** your robot is `robot08`, domain ID `8`. Your neighbor's is `robot09`, domain ID `9`. You're on the same Wi-Fi and the same subnet. Why don't you see each other's topics?

## Part 9 — Teach the Robot Its Hardware, Then Autostart

**Goal:** the robot has permanent names for its USB devices, then starts its own bringup at power-on. No typing.

*Robot Pi only. Do this over SSH from your laptop. You'll only touch the robot to plug and unplug USB cables.*

### 9.1 — Teach the Pi its USB devices

You do this over SSH from your laptop. The motor board, lidar and camera all show up as USB devices with names like `/dev/ttyUSB0`. Those numbers change between boots. A **udev rule** gives each device a permanent name. The launch file uses `/dev/rrc` (motor board) and `/dev/ldlidar` (lidar).

**Motor board.** Create the rule file:

```bash
sudo nano /etc/udev/rules.d/99-rrc.rules
```

Paste this one line, then save (Ctrl+O, Enter, Ctrl+X):

```
KERNEL=="ttyACM*", SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="55d4", SYMLINK+="rrc", MODE="0666", GROUP="dialout", ENV{ID_MM_PORT_IGNORE}="1"
```

**Lidar.** Find its USB IDs. Unplug everything except the lidar adapter, then run:

```bash
lsusb
```

The lidar adapter is the new line. The two codes after `ID` are `<vendor>:<product>`. Example: `ID 10c4:ea60` means vendor `10c4`, product `ea60`.

**Confirm with the device itself (the lidar should appear as `ttyUSB0`):**

```bash
udevadm info -a -n /dev/ttyUSB0 | grep -E "idVendor|idProduct" | head -2
```

> **Write down:** vendor `________` product `________`

Create the lidar rule file:

```bash
sudo nano /etc/udev/rules.d/99-ldlidar.rules
```

Paste this line, replacing `VVVV` and `PPPP` with **your** vendor and product codes:

```
SUBSYSTEM=="tty", ATTRS{idVendor}=="VVVV", ATTRS{idProduct}=="PPPP", SYMLINK+="ldlidar", MODE="0666"
```

**Depth camera.** The camera package ships its own rule file. Find it and copy it:

```bash
find ~/ros2_ws/src/ascamera -name "angstrong-camera.rules"
```

```bash
sudo cp <path-printed-above> /etc/udev/rules.d/
```

**Load all the new rules:**

```bash
sudo udevadm control --reload-rules && sudo udevadm trigger
```

Now **unplug and replug the lidar, camera and motor board**, then check the names exist:

```bash
ls -l /dev/rrc /dev/ldlidar
```

☐ Both names print and point at a `ttyACM` or `ttyUSB` device. If one is missing, re-check the vendor/product codes for that device.

### 9.2 — Autostart: a robot that wakes up ready

**systemd** is the part of Linux that starts things at boot. A **service file** tells it what to run, as who, and when.

> **Safety first.** Put the robot on a stand or give it clear floor before you test this. A robot that starts itself might also move itself.

*Robot Pi only.*

**What the launch file starts.** Open `robot.launch.py` in your repo (`mentorpi/mentorpi_bringup/launch/`) and read it. It starts the motor driver, the robot description, odometry, the lidar, and the depth camera. Nothing else runs at boot.

**One thing the launch file must do first: set `MACHINE_TYPE`.** Hiwonder's robot description and its odometry node both read an environment variable named `MACHINE_TYPE`. A service started by systemd doesn't load your terminal settings, so without this the robot fails at boot. Check that these two lines are near the top of `robot.launch.py`:

```python
import os
os.environ.setdefault('MACHINE_TYPE', 'MentorPi_Mecanum')
```

`setdefault` only sets the value if nothing else already did, so it's safe to leave in.

**On the robot Pi (SSH). Write the service file** (`$USER` fills in your username):

```bash
sudo tee /etc/systemd/system/robot-bringup.service > /dev/null <<EOF
[Unit]
Description=Robot bringup (ROS 2)
After=network-online.target
Wants=network-online.target

[Service]
User=${USER}
EnvironmentFile=/etc/robot.env
Environment=PYTHONUNBUFFERED=1
ExecStart=/bin/bash -c 'source /opt/ros/jazzy/setup.bash && source /home/${USER}/ros2_ws/install/setup.bash && exec ros2 launch mentorpi_bringup robot.launch.py'
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF
```

What each section does:
- `After=network-online.target`: wait for Wi-Fi first
- `User=` and `EnvironmentFile=`: run as you, with your `/etc/robot.env` settings
- `ExecStart=`: the one command that starts the robot
- `Restart=on-failure`: if it crashes, try again in 5 seconds
- `WantedBy=multi-user.target`: start at boot

**Tell systemd about the new file:**

```bash
sudo systemctl daemon-reload
```

**Start it now and at every boot:**

```bash
sudo systemctl enable --now robot-bringup.service
```

**Is it running? (look for `active (running)`)**

```bash
systemctl status robot-bringup.service
```

**Watch its output live (`Ctrl+C` to stop watching; the robot keeps running):**

```bash
journalctl -u robot-bringup -f
```

**The real test: reboot.**

```bash
sudo reboot
```

Wait about a minute. Then, on your laptop (load `~/robot_env.sh` first), without touching the robot:

```bash
ros2 topic list
```

You should see the robot's topics. Find the **lidar** (`/scan_raw`), **odometry** (`/odom`) and **camera** topics in the list. You'll use them in Module 12.

☐ After a reboot, with nobody logged in, your laptop sees the robot's topics.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Pi shows no picture | Monitor wasn't plugged in at boot | Plug in the monitor first (use the HDMI port next to the USB-C power), then power on |
| `ping ubuntu.com` fails on guest Wi-Fi | Portal not accepted, or it timed out | Open Firefox, accept the terms again |
| `ROS_APT_SOURCE_VERSION` is blank | GitHub limits requests per address, and the whole lab shares one | Wait a few minutes, or ask your instructor for the version number and set it by hand |
| `apt` can't find `ros-jazzy-...` | Package source missing | On the Pi, redo 4.3, then `sudo apt update` |
| `sudo rosdep init` says file exists | Already initialized | Fine. Go on to `rosdep update` |
| `colcon build` fails on the robot Pi | Missing dependency | Re-run the `rosdep install` command. Read the first error, not the last |
| `colcon build` says duplicate package names | The same package is in two folders under `src/` | Keep each repo in its own folder next to `mentorpi`. Don't copy packages into your repo |
| `ros2 pkg prefix mentorpi_description` fails on the laptop | Package not built, or `setup.bash` not loaded | Re-run the laptop build in 4.8, then `source ~/robot_env.sh` |
| `/dev/rrc` or `/dev/ldlidar` missing | Wrong vendor/product code, or rules not reloaded | Redo 9.1 for that device, then unplug and replug it |
| `netplan generate` complains about permissions | File is readable by everyone | `sudo chmod 600 /etc/netplan/90-robot-network.yaml` |
| `netplan generate` complains about syntax | YAML indentation | Spaces only, no tabs. Compare to Part 5 line by line |
| Pi didn't join `Rogue_Network` | Guest Wi-Fi won instead | Turn off its autoconnect (5.3), then `sudo nmcli connection up netplan-wlan0-Rogue_Network` |
| Pi lost the network completely | Typo in the Netplan file | Plug in the monitor, fix `/etc/netplan/90-robot-network.yaml`, run `sudo netplan apply` |
| Laptop won't join `Rogue_Network` | Wrong password in the `nmcli` command | `sudo nmcli connection delete Rogue_Network`, then redo 5.4 |
| Laptop has no internet | It's still on `Rogue_Network` | Switch back to the guest network (end of 5.4) |
| Laptop can't ping the robot | Wrong address on one computer, or laptop isn't on `Rogue_Network` | `ip -br addr` on each. Robot is `192.168.0.1NN`, laptop is `192.168.0.2NN` |
| `ssh` says `Connection refused` | SSH server not running | On the Pi: `sudo systemctl enable --now ssh` |
| `ssh` says `Host key verification failed` | You re-flashed the card and the fingerprint changed | `ssh-keygen -R 192.168.0.1NN`, then try again |
| `.local` name doesn't work | The router blocks name discovery | Use the IP address |
| `chronyc sources` doesn't list the laptop | Laptop `chrony` config missing, not restarted, or a firewall is blocking it | On the laptop: `cat /etc/chrony/conf.d/robot-time.conf`, then `sudo systemctl restart chrony`. Check `sudo ufw status` (should say inactive). Do the same restart on the Pi |
| `ros2 topic list` is empty on the laptop | Wrong domain, or `~/robot_env.sh` isn't loaded in this terminal | `source ~/robot_env.sh`. Compare `printenv \| grep ROS` on both computers |
| Topics show up on the robot but not the laptop | DDS bound to the wrong network card, or Wi-Fi is blocking multicast | Check the Pi's `cyclonedds.xml` says `wlan0`, and the laptop's has your `192.168.0.2NN` address. Then try the unicast fallback below |
| `ROS_DOMAIN_ID ... is not an integer` | Leading zero (like `08`) | Use `$((10#${NN}))` as in Part 7 |
| Service says `failed` | Wrong launch file name, or workspace not built | `journalctl -u robot-bringup -n 50`. Read it from the **bottom** |
| Service fails mentioning `MACHINE_TYPE` | The launch file doesn't set it | Add the two lines from Part 9 to the top of `robot.launch.py`, rebuild, restart the service |
| Service runs but no topics | Started before the Wi-Fi was ready | `sudo systemctl restart robot-bringup.service`. Check `After=network-online.target` |
| Need the desktop for troubleshooting | Robot is set to headless | `sudo systemctl start gdm3` |

### Fallback: unicast discovery

If Parts 1 to 8 are right but the computers can't see each other's topics, the Wi-Fi may be blocking multicast. Each side can be told the other's address directly. The ping must work first.

**On the robot Pi** (set `NN` first):

```bash
sudo tee /etc/ros/cyclonedds.xml > /dev/null <<EOF
<CycloneDDS xmlns="https://cdds.io/config">
  <Domain Id="any">
    <General>
      <Interfaces>
        <NetworkInterface name="wlan0"/>
      </Interfaces>
      <AllowMulticast>false</AllowMulticast>
    </General>
    <Discovery>
      <Peers>
        <Peer address="192.168.0.2${NN}"/>
      </Peers>
    </Discovery>
  </Domain>
</CycloneDDS>
EOF
```

**On your laptop** (set `NN` first). The peer is the robot this time:

```bash
cat > ~/cyclonedds_lab.xml <<EOF
<CycloneDDS xmlns="https://cdds.io/config">
  <Domain Id="any">
    <General>
      <Interfaces>
        <NetworkInterface address="192.168.0.2${NN}"/>
      </Interfaces>
      <AllowMulticast>false</AllowMulticast>
    </General>
    <Discovery>
      <Peers>
        <Peer address="192.168.0.1${NN}"/>
      </Peers>
    </Discovery>
  </Domain>
</CycloneDDS>
EOF
```

Restart anything that was running (`sudo systemctl restart robot-bringup.service` on the robot, new terminals on the laptop) and test again. With this fallback you only see your own robot, so the "neighbor's robot" step in Module 12 won't work. Skip it.
