# Lab 11 — Bringing Up a Robot: Raspberry Pi, Network, and ROS 2


## Part 1 — Flash the SD Card

**Goal:** Ubuntu Desktop 24.04 on the card.

On your lab computer, open **Raspberry Pi Imager** and choose:

1. **Device:** Raspberry Pi 5
2. **Operating System:** Other general-purpose OS → Ubuntu → **Ubuntu Desktop 24.04 LTS (64-bit)**
3. **Storage:** your microSD card
4. Write the card, then put it in the Pi.

The Raspberry Pi Imager offers custimization for Raspbian but not Ubuntu.  We need to connect a monitor and keyboard to configure the pi.

**Plug in the monitor, keyboard, and mouse first, then power.** The Raspberry Pi only checks for a monitor at boot and disables the GUI (desktop environment) if no monitor is detected.

## Part 2 — First Boot and the Setup Wizard

**Goal:** a Pi with your name, your computer name, and your account.

The first boot takes a few minutes. Work through the wizard. When it asks about **your name, your computer's name, and username**, here is what each one actually does:

| Wizard field | What it's for | Why it matters |
|---|---|---|
| **Your name** | The friendly name on the login screen ("Welcome, Alex") | Nothing technical depends on it. Use whatever you like |
| **Your computer's name** | The **hostname**: how the robot shows up on the network and in your terminal prompt (`user@robot03`) | It has to be **unique**, because it's how you tell robots apart. Use `robotNN`, lowercase, no spaces or underscores |
| **Username** | The login **account**. It sets your home folder (`/home/username`) and is what you type in `ssh username@...` | The autostart service runs *as this user*, and it's a pain to change later. Use the one your instructor gave you |
| **Password** | Needed for `sudo` and for SSH | You'll type it a lot. Don't forget it |

Use **Central Time** and the US keyboard layout.

Skip the WiFi configuration for now.

When you see the desktop, open the terminal.

**Check the names stuck (open a terminal on the Pi):**

```bash
hostnamectl
```

Look at **Static hostname**. If it isn't `robotNN`, fix it (replace `robot03` with yours):

```bash
sudo hostnamectl set-hostname robot03
```

**Check your understanding:** two robots both named `ubuntu` are on the same network. What goes wrong?

### 4.6 — Teach the robot Pi its USB devices

The motor board, lidar and camera all show up as USB devices with names like `/dev/ttyUSB0`. Those numbers change between boots. A **udev rule** gives each device a permanent name. The launch file uses `/dev/rrc` (motor board) and `/dev/ldlidar` (lidar).

**Motor board.** Create the rule file:

```bash
sudo nano /etc/udev/rules.d/99-rrc.rules
```

Paste this one line, then save (Ctrl+O, Enter, Ctrl+X):

```
KERNEL=="ttyACM*", SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="55d4", SYMLINK+="rrc", MODE="0666", GROUP="dialout", ENV{ID_MM_PORT_IGNORE}="1"
```

**Lidar.** Find its USB IDs. Unplug everything except the lidar adapter, then run:

```bash
lsusb
```

The lidar adapter is the new line. The two codes after `ID` are `<vendor>:<product>`. Example: `ID 10c4:ea60` means vendor `10c4`, product `ea60`.

**Confirm with the device itself (the lidar should appear as `ttyUSB0`):**

```bash
udevadm info -a -n /dev/ttyUSB0 | grep -E "idVendor|idProduct" | head -2
```

> **Write down:** vendor `________` product `________`

Create the lidar rule file:

```bash
sudo nano /etc/udev/rules.d/99-ldlidar.rules
```

Paste this line, replacing `VVVV` and `PPPP` with **your** vendor and product codes:

```
SUBSYSTEM=="tty", ATTRS{idVendor}=="VVVV", ATTRS{idProduct}=="PPPP", SYMLINK+="ldlidar", MODE="0666"
```

> **Instructor:** after you run `lsusb` on a real MentorPi, replace `VVVV` and `PPPP` here with the real codes so students can paste it directly. (Many LD19 kits use a CP210x adapter, `10c4:ea60`. Confirm on your units.)

**Depth camera.** The camera package ships its own rule file. Find it and copy it:

```bash
find ~/ros2_ws/src/ascamera -name "angstrong-camera.rules"
```

```bash
sudo cp <path-printed-above> /etc/udev/rules.d/
```

**Load all the new rules:**

```bash
sudo udevadm control --reload-rules && sudo udevadm trigger
```

Now **unplug and replug the lidar, camera and motor board**, then check the names exist:

```bash
ls -l /dev/rrc /dev/ldlidar
```

☐ Both names print and point at a `ttyACM` or `ttyUSB` device. If one is missing, re-check the vendor/product codes for that device.

## Part 5 — Netplan: Move to the Robot Network

**Goal:** the Pi joins `RAS-Robots` at `192.168.1.1NN` every time it boots.

**Netplan** is Ubuntu's network config system. You write a YAML file describing what you want, and Netplan turns it into settings for NetworkManager.

> **Do this part at the Pi's own keyboard and monitor, not over SSH.** If you make a typo, you lose the network, and the monitor is how you fix it.

### 5.1 — Look before you change

**What are the network cards called? (The Wi-Fi one should be `wlan0`.)**

```bash
ip -br addr
```

**What Netplan files already exist?**

```bash
ls /etc/netplan
```

Netplan reads files in alphabetical order, and later files win. Ours is named `90-robot-network.yaml`, so it goes last.

### 5.2 — Write the file

**Set your robot number (same terminal for the next two commands; change `01` to yours):**

```bash
NN=01
WIFI_PW='password-from-your-instructor'
```

**Create the Netplan file:**

```bash
sudo tee /etc/netplan/90-robot-network.yaml > /dev/null <<EOF
network:
  version: 2
  renderer: NetworkManager
  wifis:
    wlan0:
      dhcp4: false
      addresses: [192.168.1.1${NN}/24]
      access-points:
        "RAS-Robots":
          password: "${WIFI_PW}"
EOF
```

**Look at what you wrote. Is the address right? (Robot 03 should show `192.168.1.103/24`.)**

```bash
sudo cat /etc/netplan/90-robot-network.yaml
```

Notice there's **no gateway and no DNS**. The robot network has no internet, so there's nowhere to send that traffic anyway.

**Lock the file down (it has a Wi-Fi password in it, and Netplan complains if other users can read it):**

```bash
sudo chmod 600 /etc/netplan/90-robot-network.yaml
```

### 5.3 — Apply it

**Check the YAML for mistakes (no output means it's good):**

```bash
sudo netplan generate
```

**Apply it:**

```bash
sudo netplan apply
```

**Tell the Pi to stop auto-joining the guest Wi-Fi, so it doesn't wander back. First find its name:**

```bash
nmcli connection show
```

**Then turn off its autoconnect (put the guest connection's name in the quotes):**

```bash
sudo nmcli connection modify "KSU-Guest-Name-Here" connection.autoconnect no
```

**If the Pi is still on the guest network, switch it by hand:**

```bash
sudo nmcli connection up netplan-wlan0-RAS-Robots
```

### 5.4 — Check it

**Do you have the right address?**

```bash
ip -br addr show wlan0
```

**Can you reach the router?**

```bash
ping -c 3 192.168.1.1
```

**Now go to your lab computer (open a terminal in the lab environment). Is the lab computer's robot network card set up?**

```bash
ip -br addr
```

You should see `192.168.1.2NN` on one of the cards. If you don't, tell your instructor.

**Can the lab computer see the robot? (replace `103` with yours)**

```bash
ping -c 3 192.168.1.103
```

☐ The robot answers the lab computer's ping.

> **No internet on the robot now, and that's correct.** If you ever need updates again, reconnect it to the guest Wi-Fi with `nmcli`.

## Part 7 — ROS 2 Network Settings

**Goal:** the robot and your lab computer speak the same ROS 2 dialect, and nobody else's robot hears you.

Four settings matter:

| Setting | What it does |
|---|---|
| `ROS_DOMAIN_ID` | Your private channel. Same number on your robot and lab computer, so you only hear *your* robot |
| `RMW_IMPLEMENTATION` | Which DDS library carries the messages. Both sides must match. We use CycloneDDS |
| `ROS_AUTOMATIC_DISCOVERY_RANGE` | How far to look for other ROS nodes. `SUBNET` means this network only |
| `CYCLONEDDS_URI` | Points to a config file that pins CycloneDDS to the right network card |

### On the robot (over SSH)

**Set your robot number again (a new terminal forgets it):**

```bash
NN=01
```

**Make the config folder:**

```bash
sudo mkdir -p /etc/ros
```

**Write the CycloneDDS config (this pins it to the Wi-Fi card):**

```bash
sudo tee /etc/ros/cyclonedds.xml > /dev/null <<'EOF'
<CycloneDDS xmlns="https://cdds.io/config">
  <Domain Id="any">
    <General>
      <Interfaces>
        <NetworkInterface name="wlan0"/>
      </Interfaces>
      <AllowMulticast>spdp</AllowMulticast>
    </General>
  </Domain>
</CycloneDDS>
EOF
```

**Write the settings file (the `10#` keeps `08` from being read as octal):**

```bash
sudo tee /etc/robot.env > /dev/null <<EOF
ROS_DOMAIN_ID=$((10#${NN}))
RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET
CYCLONEDDS_URI=file:///etc/ros/cyclonedds.xml
EOF
```

**Check it (robot 03 should show `ROS_DOMAIN_ID=3`):**

```bash
cat /etc/robot.env
```

**Make every new terminal load these settings and ROS 2:**

```bash
echo 'set -a; source /etc/robot.env; set +a' >> ~/.bashrc
```

```bash
echo 'source /opt/ros/jazzy/setup.bash' >> ~/.bashrc
```

```bash
echo 'source ~/ros2_ws/install/setup.bash' >> ~/.bashrc
```

**Load them into this terminal now:**

```bash
source ~/.bashrc
```

**Confirm:**

```bash
printenv | grep -E 'ROS|RMW|CYCLONE'
```

### On the lab computer

The lab computer needs the **same domain and DDS library**, but a config pinned to *its* robot-network card (found by its address, since the card name varies).

**Set your robot number:**

```bash
NN=01
```

**Write the config:**

```bash
cat > ~/cyclonedds_lab.xml <<EOF
<CycloneDDS xmlns="https://cdds.io/config">
  <Domain Id="any">
    <General>
      <Interfaces>
        <NetworkInterface address="192.168.1.2${NN}"/>
      </Interfaces>
      <AllowMulticast>spdp</AllowMulticast>
    </General>
  </Domain>
</CycloneDDS>
EOF
```

**Set the variables (do this in every new terminal on the lab computer):**

```bash
export ROS_DOMAIN_ID=$((10#${NN}))
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET
export CYCLONEDDS_URI=file://$HOME/cyclonedds_lab.xml
```

**Make sure CycloneDDS is installed on the lab computer (it should print a path):**

```bash

```

### The robot's clock

**Check the date and time on the robot:**

```bash

```

The Pi has no battery-backed clock by default. With no internet, it can wake up thinking it's the wrong day. Later, ROS 2 uses timestamps to match sensor data to positions, and a wrong clock breaks that. Your instructor may set the lab computer as a time source for the robot. If so, they'll give you one line to add to `/etc/chrony/chrony.conf`.

## Part 9 — Autostart: A Robot That Wakes Up Ready

**Goal:** the robot starts its own bringup at power-on. No SSH, no typing.

**systemd** is the part of Linux that starts things at boot. A **service file** tells it what to run, as who, and when.

> **Safety first.** Put the robot on a stand or give it clear floor before you test this. A robot that starts itself might also move itself.

**Back on the robot (SSH). Write the service file** (`$USER` fills in your username, and `robot.launch.py` is the launch file your instructor named for the real robot):

```bash
sudo tee /etc/systemd/system/robot-bringup.service > /dev/null <<EOF
[Unit]
Description=Robot bringup (ROS 2)
After=network-online.target
Wants=network-online.target

[Service]
User=${USER}
EnvironmentFile=/etc/robot.env
Environment=PYTHONUNBUFFERED=1
ExecStart=/bin/bash -c 'source /opt/ros/jazzy/setup.bash && source /home/${USER}/ros2_ws/install/setup.bash && exec ros2 launch mentorpi_bringup robot.launch.py'
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF
```

What each section does:
- `After=network-online.target`: wait for Wi-Fi first
- `User=` and `EnvironmentFile=`: run as you, with your `/etc/robot.env` settings
- `ExecStart=`: the one command that starts the robot
- `Restart=on-failure`: if it crashes, try again in 5 seconds
- `WantedBy=multi-user.target`: start at boot

**Tell systemd about the new file:**

```bash
sudo systemctl daemon-reload
```

**Start it now and at every boot:**

```bash
sudo systemctl enable --now robot-bringup.service
```

**Is it running? (look for `active (running)`)**

```bash
systemctl status robot-bringup.service
```

**Watch its output live (`Ctrl+C` to stop watching; the robot keeps running):**

```bash
journalctl -u robot-bringup -f
```

**The real test: reboot.**

```bash
sudo reboot
```

Wait about a minute. Then, on your lab computer (variables set), without touching the robot:

```bash
ros2 topic list
```

You should see the robot's topics. Find the **lidar** and **camera** topics in the list. You'll use them in Module 12.

☐ After a reboot, with nobody logged in, the lab computer sees the robot's topics.

**Check your understanding:** a classmate SSHes in, runs `ros2 launch ...` by hand, and logs out. Their robot stops. Yours doesn't. Why?

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Pi 5 shows no picture | Monitor wasn't plugged in at boot | Plug in the monitor first (use the HDMI port next to the USB-C power), then power on |
| `ping ubuntu.com` fails on guest Wi-Fi | Portal not accepted, or it timed out | Open Firefox, accept the terms again |
| `ROS_APT_SOURCE_VERSION` is blank | GitHub limits requests per address, and the whole lab shares one | Wait a few minutes, or ask your instructor for the version number and set it by hand |
| `apt` can't find `ros-jazzy-...` | Package source missing | Redo 4.3, then `sudo apt update` |
| `sudo rosdep init` says file exists | Already initialized | Fine. Go on to `rosdep update` |
| `colcon build` fails on the Pi | Missing dependency | Re-run the `rosdep install` command. Read the first error, not the last |
| `netplan generate` complains about permissions | File is readable by everyone | `sudo chmod 600 /etc/netplan/90-robot-network.yaml` |
| `netplan generate` complains about syntax | YAML indentation | Spaces only, no tabs. Compare to Part 5 line by line |
| Pi didn't join `RAS-Robots` | Guest Wi-Fi won instead | Turn off its autoconnect (5.3), then `sudo nmcli connection up netplan-wlan0-RAS-Robots` |
| Pi lost the network completely | Typo in the Netplan file | Plug in the monitor, fix `/etc/netplan/90-robot-network.yaml`, run `sudo netplan apply` |
| `ssh` says `Connection refused` | SSH server not running | On the Pi: `sudo systemctl enable --now ssh` |
| `ssh` says `Host key verification failed` | You re-flashed the card and the robot's fingerprint changed | `ssh-keygen -R 192.168.1.1NN`, then try again |
| `.local` name doesn't work | Name discovery doesn't cross into the container | Use the IP address |
| `ros2 topic list` is empty on the lab computer | Wrong domain, or the variables aren't set in this terminal | Re-run the `export` lines. Compare `printenv \| grep ROS` on both sides |
| Topics show up on the robot but not the lab computer | DDS bound to the wrong network card | Check `cyclonedds.xml` (robot: `wlan0`; lab computer: the `192.168.1.2NN` address) |
| Still nothing, and the config looks right | The lab environment isn't using the computer's network directly | Ask your instructor to check the container's network mode |
| `ROS_DOMAIN_ID ... is not an integer` | Leading zero (like `08`) | Use `$((10#${NN}))` as in Part 7 |
| Service says `failed` | Wrong launch file name, or workspace not built | `journalctl -u robot-bringup -n 50`. Read it from the **bottom** |
| Service runs but no topics | Started before the Wi-Fi was ready | `sudo systemctl restart robot-bringup.service`. Check `After=network-online.target` |
| Robot's clock is wrong after boot | No internet and no battery-backed clock | See your instructor about the lab time source |
| Need the desktop for troubleshooting | Robot is set to headless | `sudo systemctl start gdm3` |
