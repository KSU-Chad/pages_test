## Part 1 — GitHub Credentials

### Why not just use your GitHub password?

You actually can't, GitHub disabled password authentication for git operations (push, pull, clone over HTTPS) back in 2021. Some kind of token or key is now required no matter what.

But even if it were still allowed, you wouldn't want to. Here's why:

- **Scoped access, not full account access.** A token can be limited to specific repos and specific permissions. Your account password can do everything, change your email, delete repos, anything.
- **Revocable without collateral damage.** If a token leaks (a shared lab computer, a screen someone photographs, a forgotten terminal), you revoke that one token and nothing else breaks. If your actual password leaked, you'd have to change it everywhere it's used, every device, every saved login.
- **Expiration.** Tokens can be set to expire automatically. A leaked token from three months ago that already expired is a non-event. A leaked password lives forever until you notice and act.


### Your options

| Method | How it works | Good fit here? |
|---|---|---|
| SSH key (traditional) | A key pair: a private key file that stays on your machine, and a public key you add to your GitHub account | No — the private key file lives on disk and gets wiped by Deep Freeze on reboot |
| Personal access token (classic) | One long token, full account scope, paste it in place of a password | Works, but grants access to *every* repo you can access, and is a long string to copy correctly |
| Fine-grained PAT | A long token, scoped to specific repos/permissions, with an expiration date | More secure than classic, but still a long string to type/paste each session |
| Device-flow OAuth login (gh CLI) | Run one command, get a short one-time code, enter it in a browser | What we're using — GitHub's own docs actually recommend this (or Git Credential Manager) over creating a PAT at all, when it's an option |
 
 ---
**A common point of confusion: passkeys, on their own, are not in this table.** A [passkey](https://docs.github.com/en/authentication/authenticating-with-a-passkey/about-passkeys) normally replaces your *password and two-factor step when signing in to github.com in a browser* — that's a separate system from authenticating `git` commands.
 

### Setting it up

1. Confirm the GitHub CLI is installed:

   ```bash
   gh --version
   ```

   If it's missing, install it first.

2. Start the login flow:

   ```bash
   gh auth login --web
   ```

3. Follow the prompts (GitHub.com, HTTPS). It will print a short one-time code and open (or tell you to open) `github.com/login/device` in a browser.

4. Enter the code on that page, sign in if needed, and click **Authorize**.

5. Back in the terminal, confirm it worked:

   ```bash
   gh auth status
   ```

6. Test it for real, `git clone`, `git push`, or `git pull` against any of your repos should now just work, no password or token prompt.

**Remember:** this is a per-session step. Once the lab computer reboots, you'll repeat steps 2-4 next time. That's expected, not a sign something went wrong.

This is the same repo you created and built your robot in back in Module 5 — you don't need a new one, and you don't need to recreate the robot.
 

## Troubleshooting Tips

- **`gh: command not found`:** it needs to be installed separately from `git`, check with your instructor if it's missing from the lab image
- **Device code expires before you finish entering it:** just re-run `gh auth login --web` for a fresh code, they're only valid for a few minutes
- **`git push` still asks for a password after `gh auth login`:** confirm you authenticated with the HTTPS protocol (not SSH) during setup, run `gh auth status` to check
- **Colcon can't find the cloned package:** confirm you cloned into `~/dev_ws/src`, not somewhere else, and that you ran `colcon build` from `~/dev_ws` (the workspace root, not inside `src`)
- **Robot spawns but immediately falls through the floor:** confirm you loaded `empty.sdf`, not an actually-empty world with no ground plane
- **Teleop doesn't respond to keypresses:** click into teleop's own terminal window first
- **Teleop runs but the robot never moves:** you're almost certainly missing the `stamped:=true` flag, see Wednesday's lecture
- **Robot drives, but turns too much or too little:** re-check the `DiffDrive` plugin's wheel separation/diameter against your actual URDF dimensions
