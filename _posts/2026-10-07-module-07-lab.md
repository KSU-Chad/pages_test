# RAS 212 — Module 7 Lab
## Bringing Up the Simulated MentorPi

**Prerequisites:** Monday's lecture and Wednesday's live walkthrough
**Format:** Six parts. Set up git, create the packages, add what Gazebo needs to the xacro, write the launch files and bridge, drive the robot, then practice git branches. 

**Lab computers reset on reboot.** Anything not pushed to GitHub is gone. Push before you leave, every session.

**Where everything lives:**

```
~/ros2_ws/
└── src/
    └── mentorpi/                  <- your git repo (a folder, not a package)
        ├── mentorpi_description/  <- Hiwonder's robot model (shared)
        └── mentorpi_bringup/      <- yours: launch files, config, xacro wrapper
```

`mentorpi_description` is "the robot." `mentorpi_bringup` is "how we run it." In Module 8, the real-robot launch files go into `mentorpi_bringup`.

## Part 2 — Gazebo Requirements in the Xacro

**Goal:** a valid robot description with the `MecanumDrive` plugin attached (in simulation only) and collision shapes Gazebo can use.

The plan: leave Hiwonder's `mentorpi.xacro` alone. Our own wrapper xacro includes it, and adds the Gazebo plugin only when `sim_mode` is true. The real robot will use the same wrapper with `sim_mode:=false`.

1. Create `mentorpi_bringup/urdf/gazebo_control.xacro`:

   ```xml
   <?xml version="1.0"?>
   <robot xmlns:xacro="http://ros.org/wiki/xacro">
     <gazebo>
       <plugin filename="gz-sim-mecanum-drive-system"
               name="gz::sim::systems::MecanumDrive">
         <front_left_joint>wheel_lf_Joint</front_left_joint>
         <front_right_joint>wheel_rf_Joint</front_right_joint>
         <back_left_joint>wheel_lb_Joint</back_left_joint>
         <back_right_joint>wheel_rb_Joint</back_right_joint>
         <wheelbase>0.1347</wheelbase>
         <wheel_separation>0.1370</wheel_separation>
         <wheel_radius>0.0325</wheel_radius>
         <frame_id>odom</frame_id>
         <child_frame_id>base_footprint</child_frame_id>
         <topic>cmd_vel</topic>
         <odom_topic>odom</odom_topic>
         <tf_topic>tf</tf_topic>
       </plugin>
       <plugin filename="gz-sim-joint-state-publisher-system"
               name="gz::sim::systems::JointStatePublisher">
         <topic>joint_states</topic>
       </plugin>
     </gazebo>
   </robot>
   ```

2. Create the wrapper, `mentorpi_bringup/urdf/robot.urdf.xacro`:

   ```xml
   <?xml version="1.0"?>
   <robot xmlns:xacro="http://www.ros.org/wiki/xacro" name="mentorpi">

     <xacro:arg name="sim_mode" default="false"/>

     <!-- The robot itself: Hiwonder's model, shared by sim and real -->
     <xacro:include filename="$(find mentorpi_description)/urdf/mentorpi.xacro"/>

     <!-- Gazebo-only parts -->
     <xacro:if value="$(arg sim_mode)">
       <xacro:include filename="$(find mentorpi_bringup)/urdf/gazebo_control.xacro"/>
     </xacro:if>

   </robot>
   ```

3. Build, then check the URDF without Gazebo. A new file needs a rebuild even with `--symlink-install`:

   **Install the URDF checker:**

   ```bash
   sudo apt install liburdfdom-tools
   ```

   **Go to the workspace root:**

   ```bash
   cd ~/ros2_ws
   ```

   **Rebuild so the new wrapper and plugin files get installed:**

   ```bash
   colcon build --symlink-install
   ```

   **Source the install (the wrapper uses `$(find ...)`, which needs it):**

   ```bash
   source install/setup.bash
   ```

   **Tell Hiwonder's xacro to use the Mecanum chassis:**

   ```bash
   export MACHINE_TYPE=MentorPi_Mecanum
   ```

   **Expand the xacro into plain URDF:**

   ```bash
   xacro src/mentorpi/mentorpi_bringup/urdf/robot.urdf.xacro sim_mode:=true > /tmp/mentorpi.urdf
   ```

   **Check the URDF and print the link tree:**

   ```bash
   check_urdf /tmp/mentorpi.urdf
   ```

   You should see `Successfully Parsed XML`, with `base_footprint` as the root link and `base_link` as its only child. The wheels, `depth_cam`, `imu_link`, and `lidar_frame` hang off `base_link`.

   Then compare: run the same `xacro` command with `sim_mode:=false` into a second file, and `diff` the two. What's the only difference?

4. Verify the four wheel joint names against the real file, instead of trusting this handout:

   ```bash
   grep -n 'joint name="wheel' ~/ros2_ws/src/mentorpi/mentorpi_description/urdf/mecanum.xacro
   ```

5. Now fix the collision shapes. Gazebo's physics engine here (dartsim) can't build collisions from meshes, so links with mesh collisions are drawn but not solid. Keep the meshes for `<visual>` and replace each `<collision>` in `mentorpi_description/urdf/mecanum.xacro` with a primitive.

   **Left wheels** (`wheel_lf_Link` and `wheel_lb_Link`):

   ```xml
   <collision>
     <origin rpy="1.5708 0 0" xyz="0 -0.0074 0"/>
     <geometry><cylinder radius="0.0325" length="0.0344"/></geometry>
   </collision>
   ```

   **Right wheels** (`wheel_rf_Link` and `wheel_rb_Link`): the same block with `xyz="0 0.0074 0"`.

   **Chassis** (`base_link`):

   ```xml
   <collision>
     <origin rpy="0 0 0" xyz="0.0029 0 0.0113"/>
     <geometry><box size="0.2119 0.1 0.0924"/></geometry>
   </collision>
   ```

   **Camera and lidar** (`depth_cam` and `lidar_frame`): delete their `<collision>` blocks.

   There are seven collision blocks in total. Confirm no mesh collision is left (this should print nothing):

   ```bash
   grep -n "<collision>" -A4 ~/ros2_ws/src/mentorpi/mentorpi_description/urdf/mecanum.xacro | grep -i "mesh"
   ```

   Rebuild and re-run the `xacro` and `check_urdf` commands from step 3 to confirm it still parses.

**Check your understanding:** where did the numbers `0.1347`, `0.1370`, and `0.0325` come from? Compute the first from the wheel joint origins in `mecanum.xacro` (front minus rear X), and compare it to Hiwonder's `0.1368` from their code. Which would you trust, and why? Also: the wheel cylinder needs `rpy="1.5708 0 0"`. Why the rotation? (Hint: check the wheel joint `axis`.)

## Part 3 — Launch Files and the Bridge

**Goal:** one launch file that publishes the robot, starts Gazebo, spawns the robot, and bridges topics.

1. Create `mentorpi_bringup/launch/rsp.launch.py`:

   ```python
   import os
   from ament_index_python.packages import get_package_share_directory
   from launch import LaunchDescription
   from launch.actions import DeclareLaunchArgument
   from launch.substitutions import Command, LaunchConfiguration
   from launch_ros.actions import Node
   from launch_ros.parameter_descriptions import ParameterValue


   def generate_launch_description():
       os.environ.setdefault('MACHINE_TYPE', 'MentorPi_Mecanum')

       use_sim_time = LaunchConfiguration('use_sim_time')
       sim_mode = LaunchConfiguration('sim_mode')
       xacro_file = os.path.join(
           get_package_share_directory('mentorpi_bringup'),
           'urdf', 'robot.urdf.xacro')

       robot_description = ParameterValue(
           Command(['xacro ', xacro_file, ' sim_mode:=', sim_mode]), value_type=str)

       return LaunchDescription([
           DeclareLaunchArgument('use_sim_time', default_value='false'),
           DeclareLaunchArgument('sim_mode', default_value='false'),
           Node(
               package='robot_state_publisher',
               executable='robot_state_publisher',
               output='screen',
               parameters=[{'robot_description': robot_description,
                            'use_sim_time': use_sim_time}],
           ),
       ])
   ```

   `MACHINE_TYPE` is set here because Hiwonder's xacro reads it from the environment. `sim_mode` is passed through to the xacro, so the same file will serve the real robot later with `sim_mode:=false`.

2. Create `mentorpi_bringup/launch/launch_sim.launch.py`:

   ```python
   import os
   from ament_index_python.packages import get_package_share_directory
   from launch import LaunchDescription
   from launch.actions import (AppendEnvironmentVariable, DeclareLaunchArgument,
                               IncludeLaunchDescription)
   from launch.launch_description_sources import PythonLaunchDescriptionSource
   from launch.substitutions import LaunchConfiguration
   from launch_ros.actions import Node


   def generate_launch_description():
       pkg = get_package_share_directory('mentorpi_bringup')
       gz_pkg = get_package_share_directory('ros_gz_sim')

       world = LaunchConfiguration('world')

       # Gazebo turns package:// mesh paths into model:// paths and looks for them
       # in GZ_SIM_RESOURCE_PATH. Point it at the folder that contains our package.
       desc_share = os.path.dirname(get_package_share_directory('mentorpi_description'))
       gz_resources = AppendEnvironmentVariable('GZ_SIM_RESOURCE_PATH', desc_share)

       rsp = IncludeLaunchDescription(
           PythonLaunchDescriptionSource(os.path.join(pkg, 'launch', 'rsp.launch.py')),
           launch_arguments={'use_sim_time': 'true',
                             'sim_mode': 'true'}.items())

       gazebo = IncludeLaunchDescription(
           PythonLaunchDescriptionSource(os.path.join(gz_pkg, 'launch', 'gz_sim.launch.py')),
           launch_arguments={'gz_args': ['-r -v4 ', world],
                             'on_exit_shutdown': 'true'}.items())

       spawn = Node(
           package='ros_gz_sim',
           executable='create',
           arguments=['-topic', 'robot_description', '-name', 'mentorpi', '-z', '0.05'],
           output='screen')

       bridge = Node(
           package='ros_gz_bridge',
           executable='parameter_bridge',
           parameters=[{'config_file': os.path.join(pkg, 'config', 'gz_bridge.yaml'),
                        'use_sim_time': True}],
           output='screen')

       return LaunchDescription([
           DeclareLaunchArgument('world', default_value='empty.sdf'),
           gz_resources,
           rsp,
           gazebo,
           spawn,
           bridge,
       ])
   ```

3. Create `mentorpi_bringup/config/gz_bridge.yaml`:

   ```yaml
   - ros_topic_name: "clock"
     gz_topic_name: "clock"
     ros_type_name: "rosgraph_msgs/msg/Clock"
     gz_type_name: "gz.msgs.Clock"
     direction: GZ_TO_ROS

   - ros_topic_name: "cmd_vel"
     gz_topic_name: "cmd_vel"
     ros_type_name: "geometry_msgs/msg/TwistStamped"
     gz_type_name: "gz.msgs.Twist"
     direction: ROS_TO_GZ

   - ros_topic_name: "odom"
     gz_topic_name: "odom"
     ros_type_name: "nav_msgs/msg/Odometry"
     gz_type_name: "gz.msgs.Odometry"
     direction: GZ_TO_ROS

   - ros_topic_name: "tf"
     gz_topic_name: "tf"
     ros_type_name: "tf2_msgs/msg/TFMessage"
     gz_type_name: "gz.msgs.Pose_V"
     direction: GZ_TO_ROS

   - ros_topic_name: "joint_states"
     gz_topic_name: "joint_states"
     ros_type_name: "sensor_msgs/msg/JointState"
   ```

## Troubleshooting Tips

**Git**
- **`git commit` says "Author identity unknown":** run the two `git config --global` commands from Part 0
- **`git push` fails with "Permission denied (publickey)" or asks for an SSH passphrase:** your repo's remote is the SSH link. Run `git remote -v` to check. If it starts with `git@github.com:`, switch it: `git remote set-url origin https://github.com/<your-username>/mentorpi.git`
- **`git push` asks for a username and password:** you aren't logged in this session. Run `gh auth login --web` again, and choose HTTPS
- **Device code expires before you finish entering it:** re-run `gh auth login --web` for a fresh code. They only last a few minutes
- **`fatal: not a git repository`:** you're not inside `~/ros2_ws/src/mentorpi`. `cd` there and try again
- **`git clone` says the destination path `mentorpi` already exists:** you cloned earlier this session. `cd ~/ros2_ws/src/mentorpi` and use `git pull` instead
- **`git push` says "no upstream branch" on a new branch:** use `git push -u origin <branch-name>` the first time
- **`git switch` refuses because of uncommitted changes:** commit them first (or `git stash`)

**Build and launch**
- **`colcon build` fails with `File exists` on a symlink:** delete the old build output for that package, then rebuild: `rm -rf build/mentorpi_description install/mentorpi_description`
- **Package builds, but the folder name doesn't match `package.xml`:** rename the folder to match the package name
- **`colcon` doesn't find your packages:** they must be inside `~/ros2_ws/src/` (the `mentorpi/` repo folder is fine; `colcon` looks inside it). Run `colcon build` from `~/ros2_ws`, not from `src`
- **`xacro` says it can't find the file:** you're in the wrong folder, or you haven't run `source install/setup.bash`. `$(find ...)` needs both packages built and sourced
- **`xacro` complains about `MACHINE_TYPE`:** export it in your terminal: `export MACHINE_TYPE=MentorPi_Mecanum`
- **New launch, config, or xacro file isn't found:** rebuild. `--symlink-install` only covers files that already existed
- **`ros2 launch mentorpi_bringup ...` can't find the package:** run `source install/setup.bash` in that terminal
- **Launch can't find `gz_bridge.yaml`:** you created it after the last build. Rebuild `mentorpi_bringup`

**Simulation**
- **Gazebo opens but the robot isn't there (or has no body):** look in the terminal for `Unable to find file with URI [model://...]`. That means the `GZ_SIM_RESOURCE_PATH` lines in `launch_sim.launch.py` are missing or wrong
- **Robot is visible but sinks or falls through the floor:** look for `couldn't be created` in the log. That means a `<collision>` still uses a mesh; re-run the `grep` from Part 2
- **Only some wheels respond:** check every joint name in `gazebo_control.xacro` against the `grep` from Part 2, exactly
